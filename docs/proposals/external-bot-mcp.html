Mezair through MCP

Expose Mezair as a delegated MCP service for Grok Bot, OpenAI dots and other clients. Keep execution on trusted hosts, make every connection’s authority explicit, and disclose exactly where readable data goes.

Recommendation: build one capability and policy layer with two equally supported operating models: an owner-hosted daemon and a managed service with scoped execution. Develop and pilot both in parallel; let each connection choose its execution location and disclosure boundary.

Scope: Desktop, Sync & Mesh, daemon, Cloud and Registry. All API names, settings and examples below are proposed unless marked as existing. No production behaviour is changed by this document.

Delegate work, without handing over the account.

A bot should be able to find context, start and steer work, run factories, inspect results and deliver reviewed changes. “Full power” means coverage of Mezair’s workflows under configurable authority. It does not require exporting encryption keys or making every connection an unrestricted administrator.

  • Make the bot a delegated principal. Bind it to a connection, owner, selected workspaces, repositories, execution hosts and an expiring grant.
  • Keep the account key on trusted Mezair devices. Reuse scoped projections and task keys when work leaves that device.
  • Enforce policy where work happens. Tool discovery, the MCP gateway and the executor all check permissions; the executor is the final authority.
  • Make sensitive actions reviewable. Publication, delivery and destruction use immutable proposals, explicit authority and durable receipts.
  • Make broad access an informed choice. A restricted connection is the default; an owner can enable more capabilities without disabling the policy boundary.

The unavoidable disclosure: a hosted bot’s provider can read the tool results supplied to it. A gateway that terminates ordinary MCP HTTPS can also read those requests and results. Encrypted sync can stay intact, but it cannot make plaintext invisible after an authorised tool returns it.

How it works at a glance

Choose either operating model. Both enforce the same permission contract; the managed option receives only the data and scoped keys you explicitly provision.

Choose where plaintext is allowed.

Both operating models separate the owner, the execution host and the bot connection. Owner-hosted execution prioritises control of infrastructure; managed execution prioritises availability while the owner’s devices are offline. Neither is the default recommendation. The executor decrypts authorised data, performs the operation and returns a filtered result. The existing coordination backend continues to carry opaque sync content.

See the high-level diagram for both execution paths and the separate encrypted coordination channel.

Separate encrypted path: trusted devices ↔ Sync & Mesh coordinator ↔ authorised recipients. Account data keys never travel to the bot. The coordinator still sees routing, timing, sizes and orchestration metadata.

Two equal options · one permission model

Choose an owner-hosted daemon for infrastructure control, or a managed service for authorised work while your devices are offline. Both expose the same typed capability contract and review controls; available data and host capabilities are explicit.

Private OpenAI route: evaluate Secure MCP Tunnel for eligible private deployments. It changes reachability, not the fact that OpenAI receives tool results. Public plugin distribution still needs a stable public HTTPS endpoint. [W9]

Managed availability contract: during setup, a trusted device supplies selected snapshots and projected state, scoped keys and named credential-use grants. A managed workspace can continue authorised reads, edits, runs and delivery against that material while owner devices are offline, subject to adapter capability and grant expiry. Independently authorised repository or service connections can refresh their own data; unsynchronised local files and undisclosed encrypted account history remain unavailable. Return source revision, digest, capture time and freshness with results; enforce each grant’s maximum source age. Broader scopes or fresh local material require renewed provisioning. A managed forwarding endpoint alone cannot provide this availability.

Owner devices being offline does not mean the managed worker is disconnected: it must still check live grants and revocation. Use bounded leases only during control-plane outages. Recheck current remote HEAD and target state before publication; actions needing a fresh human decision remain pending until an authorised review surface supplies it. Seal results to approved recipients for later trusted-device import; an ADK-free worker cannot write ordinary account-sync ciphertext itself. Switching an owner-hosted connection to managed execution requires an explicit grant change, never silent failover.

Use per-task material and approved projections for managed execution. Do not escrow the ADK to achieve “always on”. Giving a managed runtime the account-wide ADK would be a different, broader trust model outside both options proposed here. Sending encrypted MCP results through an opaque relay would require a crypto-capable client adapter; ordinary remote MCP support does not supply that extension, so it is not the compatibility baseline.

The encryption model can stay intact.

The existing model already distinguishes authentication, device trust and narrowly shared content. Apply the same distinction to MCP. A valid OAuth token authorises a request; it cannot decrypt a sync envelope. [R3]

Preserve these guarantees

  • Seal private inputs before enqueueing; missing keys mean waiting or rejection, never plaintext fallback.
  • Use authenticated envelopes and existing reviewed crypto primitives; include replay protection and recipient binding.
  • Keep secret values, provider OAuth caches and share-link keys out of logs, ordinary results and hosted audit metadata.
  • Use OS-backed storage or the explicitly configured encrypted vault on each execution host.

State these limits plainly

  • Read permission is permission to disclose that content to the bot provider.
  • Summaries and secret scanning reduce exposure; they do not prove that confidential content cannot leak.
  • Revocation cannot erase plaintext, retained keys or completed external actions.
  • Current automatic device admission trusts account authentication and service attestation. Manual verification remains the stronger independent identity check.

Bot revocation should not rotate the whole account key. Revoke the delegated grant, credentials and connection keys; fence queued work and late results. ADK rotation remains the response to trusted-device revocation or compromise. Offline executors must stop when their bounded authorisation lease expires. [R3]

Controls that compose, rather than disappear.

Effective authority = account policy ∩ connection grant ∩ workspace policy ∩ executor capability ∩ current operation approval. A denial at any layer wins. Re-evaluate before execution, before each external side effect and before returning data.

Unrestricted shell changes the trust model. A process on the same unsandboxed host as account keys can read beyond its working directory. A tool allowlist or cwd is not isolation. Require scoped mounts, an isolated runtime, brokered credentials and controlled egress for external execution. If an owner deliberately enables unsandboxed host execution, label it as host-equivalent authority.

The owner experience belongs in Settings → Bot connections: show provider/client identity, whether a connection is shared across bots, selected resources, disclosure level, execution location, expiry, approvals, recent activity and a prominent revoke action. Widening a grant requires the trusted owner flow; a bot may only request that change.

Connect once. Authorise every operation.

  1. Discover the service.The client reads MCP and OAuth metadata. Use the advertised canonical HTTPS resource; no credentials in URLs or share fragments.
  2. Authenticate the owner.Use the existing account identity where appropriate, with an MCP-specific OAuth authorisation layer. Device enrollment tokens are not the external API credential.
  3. Review a concrete connection.Show client identity, endpoint/host fingerprint, scope, data disclosure, shared-bot implications and expiry. Bind the resulting grant to the selected owner, executor and policy revision.
  4. Complete OAuth securely.Use authorisation code with PKCE, exact redirects, issuer/resource validation, short-lived access tokens and protected rotating refresh credentials. Prefer Client ID Metadata Documents (CIMD); support predefined clients or legacy dynamic registration only where a tested client requires it.
  5. Resolve identity from authentication.Derive owner, connection and scopes server-side. Ignore model-supplied account IDs, role claims and permission assertions.
  6. Dispatch through common policy.The executor verifies its owner-approved grant independently of gateway-supplied request fields. Reject expired, widened, wrong-account or wrong-host requests.
  7. Return the permitted projection.Redact credentials and cap content before it reaches the connector. Enforce pagination and disclosure rules on resources, tools, jobs, events and errors alike.
  8. Revoke across the lifecycle.Stop token refresh, reject new work, invalidate sessions, fence queued/late results and interrupt descendants where supported. Keep receipts for completed or uncertain side effects.

For ChatGPT plugins, use OAuth 2.1 with protected-resource and authorisation-server metadata. Arbitrary API keys and machine-to-machine grants are not the universal plugin onboarding route. Start with a personal plugin; published distribution is a later step. [W8]

Do not pass tokens through. A GitHub, WorkOS, model-provider or device token is not accepted as an MCP bearer token. The executor uses a named, separately scoped credential through the relevant service; the bot does not receive its value. OAuth audience checks and consent remain mandatory even behind a tunnel. Normative security requirements.

Protocol compatibility is a separate workstream

The current MCP specification is 2026-07-28, with stateless requests and per-request capability negotiation. Mezair’s existing server uses the earlier initialise/session model. Implement explicit current and legacy profiles; do not silently negotiate unsupported semantics. Keep authentication independent of any legacy MCP session ID. Cache personalised tool catalogues privately, keyed to connection and policy revision, and invalidate them when permissions change. [W6]

Use HTTPS Streamable HTTP where required by the target client, plus a local stdio adapter. Evaluate the current official SDK against legacy clients rather than extending the handwritten JSON-RPC layer by assumption. Pin supported revisions and exercise both profiles in conformance tests. Task/event extensions are optional enhancements; basic tools must remain usable without them. The official release notes document the removed handshake/session model and the move of Tasks into an extension.

Long work needs durable handles.

Most useful Mezair work outlives a single MCP request. Model a tool call as the start of a durable operation, rather than holding a network connection open until an agent finishes.

operation.start({ kind, target, input, idempotencyKey })
  → { operationId, state: "awaiting_approval", approvalId }

operation.get({ operationId })
operation.events({ operationId, afterCursor, limit })
operation.cancel({ operationId })
operation.result({ operationId, format, maxBytes })

States: queued → awaiting_approval → running → succeeded | failed
        queued/running → cancel_requested → cancelled | outcome_unknown

Illustrative contract. Use typed domain tools such as factory.run to create operations; a generic operation kind must never evade its domain’s permission checks. Expose MCP task support when the client supports it, backed by the same durable records.

Human approval

Return a pending handle and a non-secret owner review link. Review in Mezair Desktop, a suitably authorised companion, or an authenticated web surface. Bind approval to the connection, policy revision, canonical arguments, source HEAD/digest, target and expiry.

Any meaningful change invalidates the approval. The requesting bot cannot approve its own publication, broaden its grant or convert a natural-language “yes” from repository content into authority.

Retries & interruption

Persist dispatch intent before execution. Scope idempotency keys to owner, connection and operation; reject reuse with different arguments. Reconnect by durable cursor and retrieve receipts before retrying a mutation.

A cancelled request is not proof of cancelled work. Report outcome_unknown when an external publication may already have happened. Cancellation has a receipt; cleanup is verified separately.

Revocation must reach descendants. Carry the connection’s grant and policy revision into spawned agents, workflows, scheduled automations, Mesh jobs and publication checkouts. Existing automation kickoff permissions alone are insufficient to revoke a bot-originated run; add an external-grant lease checked at every consequential step.

OpenAI currently documents webhook-based MCP Events for dots; treat that as an optional adapter after portable job polling works. [W7] Optional events should contain operation IDs and minimal status. The client fetches details under current authorisation. Authenticate subscription setup, bound retries and event delivery; a webhook or notification never carries approval authority or plaintext source content by default.

Build the boundary before broadening the catalogue.

Phase 1
Extract the external principal and policy boundary.

Add shared grant/operation contracts, a single authorisation service, durable connection/approval/operation records, idempotency, receipts and explicit resource ownership checks. Implement descendant grant leases, cancellation and result fencing before the first executing pilot. Pilot local context reads, then one isolated workflow. Gate: direct calls cannot bypass scope, and revocation fences a running child and its results.

Phase 2
Pilot owner-hosted and managed operation in parallel.

Share OAuth, current/legacy protocol profiles and the capability contract. The owner-hosted track adds HTTPS, daemon registration and vault operations. The managed track adds an ADK-free gateway, isolated execution, approved snapshot/projection provisioning, credential brokering, encrypted queues and disclosure consent. Pilot Grok Bot and a dot through read → start → review → complete → revoke in both modes. Gate: tested client interoperability, documented plaintext boundaries, tenancy isolation, log/packet inspection, in-flight child revocation and rejection of late results. Managed mode must also complete authorised work while owner devices are offline and report its source freshness.

Phase 3
Cover daily development and delivery.

Expose threads, artifacts, work items, workflows, factories, scoped execution and reviewed Git/share actions. Extend the proven durable-job, receipt and revocation machinery across these domains. Gate: both operating models preserve review state; retries and changed source state cannot duplicate or bypass delivery.

Phase 4
Complete cross-product coverage.

Add Cloud, Registry, environments, integrations and richer resource/prompt discovery behind their own policies. Gate: map every user-facing operation to a tool, an explicit human-only action or a documented host limitation, with per-adapter contract tests; no expansion of current AWS or Mesh limits.

Phase 5
Harden and release both operating models.

Complete owner-hosted installation/upgrade/backup support and managed availability/retention/incident operations. Publish the same capability and policy matrix for each, with documented host limitations. Gate: recovery rehearsals, isolation and revocation checks, predictable expiry, deletion/retention behaviour and operator runbooks for both models.

Concrete implementation seams
  • src/shared/: external connection, policy, approval, operation and result contracts.
  • src/main/agent-tools/dispatch.ts: adapt caller context, tool metadata and central policy hooks; keep repository guards in domain services. Add explicit effect metadata: content read, local write, execution, network, publication, administration and secret use. The current mutation flag alone is too coarse.
  • src/main/services/agent-mcp/: preserve the local adapter; add external transport/auth adapters around shared dispatch.
  • browser-workspace-executor.service.ts and grant services: extract reusable scope/expiry/result checks without conflating browser and MCP identities.
  • Approval and workflow adapters: remove assumptions that the caller has an internal persisted chat or a live Codex session. Use a verified external principal and durable owner-review channel, with an optional linked audit thread.
  • src/daemon/: headless capability registration, vault/unlock health and remote endpoint lifecycle.
  • cloud/contract/ and backend: connection/routing/revocation metadata and encrypted forwarding envelopes; keep plaintext out of ordinary sync. A separately isolated managed execution service owns approved working copies, task keys, scoped credentials, retention and cleanup.
  • Desktop/companion/web: connection review, operation approval and audit surfaces through typed service APIs. Cloud and Registry adapters use their own explicit project credentials.

Preserve owned intent. This proposal changes no PATCH contract. Implementation should add a new external-delegation entry and update any affected existing entry in the same change, especially descendant revocation and reviewed publication behaviour.

Decisions to settle during the pilot

  1. Hosting priority is settled: support owner-hosted and managed operation equally. Confirm the owner-hosted endpoint/certificate path and managed provisioning/availability contract.
  2. Managed disclosure settings: define the approved data projection, freshness policy, hosting region, retention and credential-use limits. Require explicit consent for that scope.
  3. First capability slice: repository context → isolated factory/workflow → reviewed PR is a useful end-to-end pilot.
  4. Identity granularity: verify separate connection credentials per bot where supported; otherwise display shared account-level authority honestly.
  5. Unattended delivery: decide which actions can receive bounded standing approval and which always require a fresh owner decision.

Proposed product promise: “Connect your bot to the parts of Mezair you choose. Your account encryption key stays with your trusted devices. Choose your own host or a managed workspace, and control which data, scoped keys and actions it receives.”
